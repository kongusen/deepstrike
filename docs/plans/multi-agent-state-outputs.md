# DeepStrike 多智能体协作与上下文版本控制方案（暂缓）

> **状态：暂缓，不实施。** 评估于 2026-11-22，基于 `main`（v0.2.85）。下文第 1–7 节是 2026-11-21 的原始草案，保持原样，没有改动。
>
> **暂缓的原因**
>
> 1. **没有调用方需要它。** 现有的验证路径都按值传递、按顺序执行，候选不会在验证途中被替换：
>    - CreatorVerifier / OrchestrationMode
>    - Milestone 验证
>    - 静态 DAG 里的 verify 节点
>    - Harness 重试
>
>    动态工作流里 `ctx.parallel` 从 0.2.85 起真正并发。但动态工作流什么时候算完成，由宿主脚本自己决定：脚本拿着每次 `ctx.agent()` 的返回值，可以直接检查一份验证针对的是不是当前候选，用不着内核来裁决。
> 2. **与 [DEC-13](../decisions/013-model-led-context.md) 冲突。**
>    - P2 要求内核把模型的最终回复当作严格的 JSON 验证报告来解析，还要往子 agent 的任务说明里写入验证对象。这是内核里的语义层。
>    - 这里的"验证证据"是验证 agent 自述的 `passed: true`。绑定身份只能挡住针对旧候选的证据，不能让验证本身更可信。
>    - 第 7 节的试点指标（拒绝次数、重投命中次数）不是 DEC-13 §3 要求的成对对照测量。
> 3. **P1 大部分已经成立。**
>    - 依赖输出和继承的知识在派发时就写进启动元数据。
>    - Harness 重试复用同一份构建好的子运行输入。
>    - 派发后仍会变化的输入只有一处：full 继承的子 agent 在构建时才读取父 SessionLog，所以后续批次能看到前面兄弟节点的 `workflow_node_completed`。这属于上下文随时间变化，不是过期验证被接受。
>
> **已经单独完成的部分**
>
> - P0 租约竞态：#12，v0.2.85。
> - 草案顺带修过的动态工作流 checkpoint 恢复后 open 位丢失：#13，v0.2.85，对所有动态工作流生效。
>
> **部分实现的去向。** 原草案的部分实现在本地提交 `b3912d47` 上，从未推送，也不会合并。它有几个问题：
>
> - 一直得不到通过验证的候选时，工作流无法关闭。
> - 验证节点必须在启动时全部声明。
> - 格式不符的报告会被悄悄丢弃。
> - Node 端没有端到端测试。
>
> 如果重启这项工作，应当按第 7 节的阶段重新实现，不要恢复那份代码。
>
> **何时重新评估**：出现下面任一情况时：
>
> - 有真实的工作流需要同时替换候选和验证旧候选，并且完成与否由内核而不是宿主裁决；
> - 有测量显示 full 继承读到兄弟节点的输出、损害了子 agent 的结果。
>
> 重新评估时，先按 DEC-13 §3 设计成对测量。

## 1. 目标与首期范围

两个 Agent 可以同时读取同一份上下文，分别提出修复和验证意见。父 Workflow 在接受“任务完成”之前，要能回答三个问题：验证针对哪份产物？它是否仍是当前候选？这次完成权是否已经使用？首期以“候选产物通过验证”为完整交付场景，沿用现有 DAG、子任务 attempt 和 canonical Journal。

设计引入两项能力：派发时固定输入版本，提交时原子消费一个排他的状态输出（State Output）。证据和候选产物可以反复引用。每个共享对象归一个 operation 裁决，各 Agent 保留自己的运行上下文。协议的实施单位是一次父 Workflow，无需部署共识节点或引入全局提交链。

## 3. 派发协议：固定子 Agent 收到的输入

父运行在派发时生成一份输入清单，并在启动子运行前持久化。建议协议字段如下，具体序列化纳入共享 wire fixture。

| 字段 | 记录内容与用途 |
| --- | --- |
| 子任务身份 | 父 operation、task、attempt，定位本次派发。 |
| 父级读取边界 | 记录被读取的父 SessionLog 身份与截至哪个 session seq；另存对应的 canonical 来源位置。两份日志使用各自的游标。若无法证明二者的位置对应，先冻结所选事件的不可变副本并保存引用。 |
| 继承的知识项 | 保存来源 operation、item、可见内容 digest、可读取的内容引用，沿用 key、pin、scope 筛选。对有 pending 更新的条目取派发时实际交付的内容。 |
| 上游产物 | 为每个依赖保存生产 operation、task、attempt、内容 digest 与载荷引用。现有 dep 别名在该子运行内绑定到固定产物。即使两次执行生成相同字节，仍保留各自的来源。 |
| 强制前置条件 | 明确列出将来推进状态时需要检查的对象，如当前候选输出、测试基线或验收规则版本。普通参考资料可以自由复用。 |

派发清单说明“交付过什么”。子运行仍按现有方式按需读取正文，读取事件说明“取回过什么”。两者都不能证明模型理解了某条材料。上下文压缩、缓存重排、私有 notes 更新沿用当前机制，只有业务规则声明的前置条件变化才会影响提交。版本引用必须能解析到授权范围内的对应字节；正文已过保留期时应报告缺失，不能悄悄读取最新版本。

## 4. 提交协议：一次业务转移由谁接受

首期由父 Workflow operation 持有当前候选的状态输出。一个输出的身份可用“所属 operation、创建它的事务 ID、输出序号”确定。每次替换都生成新身份，即使再次发布内容相同的候选，旧完成请求也不能因此重新生效。

**事实提交**单独接受一项有来源的陈述，例如某次测试在基线 B 上验证了 P1，结果通过。记录应包含生产 attempt、被测产物 digest、基线、验收规则版本、结果与证据引用。接受这条记录表示保留该次验证的结果，其适用范围由这些字段限定。

**状态转移**提交一个稳定的请求 ID、操作类型、预期消费的输出 ID、必要的事实引用和规则版本。调用者身份来自已验证的运行或宿主绑定。后继输出由内核按规则产生。以完成操作为例：

1. 在所属 operation 中按请求 ID 查询回执。已接受的同 ID、同载荷返回原回执；同 ID、不同载荷返回冲突。绑定载荷时使用规范化字节与协议版本。
2. 在 prepare 中校验调用权限、当前 attempt、输入仍有效、转移类型合法。完成操作还要求验证事实的产物、基线和验收规则与当前候选匹配，证据来源满足该工作流的要求。
3. 在同一条 canonical 记录中写入消费的输入、产生的后继和被采用的事实引用。以现有 Journal CAS 提交后，内核更新活动输出与回执投影。首次发行候选由受权工作流操作完成，并检查该逻辑对象尚无当前输出。
4. CAS 冲突时恢复最新状态，以原请求、原输入重新执行 prepare。若仅有无关记录追加，可继续成功；若目标输出已被消费，返回业务冲突及可披露的当前引用。调用方如需重新基于新版本申请，应生成新请求。
5. 若持久化后进程崩溃，由恢复逻辑重建消费结果。外部测试、通知等副作用通过稳定操作 ID 和回执协调，重放只应用已记录结果。

建议向 SDK 暴露三类可处理结果：已接受（含原回执重投）、前态已变化（可重新取上下文）、请求无效（身份、证据或载荷不符）。沿用现有 attempt 对迟到完成的拒绝。若需要保存迟到的测试报告，由有权的证据入口单独接收，不能借此恢复旧 attempt 的完成权。

## 5. 用一个并发场景验收协议

| 顺序 | 已接受的事实或动作 | 当前可推进的状态 |
| --- | --- | --- |
| 1 | A 提交恢复差异的诊断和失败样例。B 提交补丁 P1。 | 父运行发行 O1，指向 P1、测试基线 B1 和规则 R1。 |
| 2 | C 收到固定的 P1 输入，开始验证。 | O1 有效。C 的报告必须标识 P1/B1/R1。 |
| 3 | B 提交 P2 的替换申请，父运行消费 O1，发行 O2。 | 当前候选为 O2。诊断、样例和 P1 仍可读取。 |
| 4 | C 返回 P1 的通过报告 V1，再以 V1 申请完成 O1。 | 报告保留。O1 已消费，完成申请返回冲突。拿 V1 申请完成 O2 也会因产物不匹配被拒。 |
| 5 | 验证者在目标基线上验证 P2，产生 V2。父运行接受对 O2 的完成申请。 | O2 被消费一次，完成输出引用 P2 与 V2。相同请求重投返回原回执。 |

替换与完成同时到达时，两者竞争同一个 O1，由同一条父 Journal 决定接受顺序。若完成先获接受，替换方必须遵守完成后重开的业务规则。后续引入排他领取时，为每个执行尝试单独生成领取输出；超时恢复消费当前领取输出并发行新输出，保留此前领取历史。

## 6. 重放、保留与跨 SDK 兼容

- **版本协商。** 新 Workflow 显式启用版本化提交。旧 Journal、旧 checkpoint 使用原协议恢复，历史依赖版本缺失时标记为未知。仅新创建、具备完整来源的候选进入严格验证流程。旧 SDK 遇到要求新能力的工作流，在启动前报告能力不匹配。
- **重放内容。** checkpoint 覆盖活动输出、裁决所需的事实绑定、已接受请求与载荷摘要和回执、规则版本，以及未完成派发的输入清单或可恢复引用。恢复从 checkpoint 加尾部记录重建；不重新调用模型、运行测试或用今天的规则重判旧事实。
- **保留边界。** 在允许裁剪 Journal 前缀前，验证 checkpoint 及其引用可恢复。需要长期复盘的事实正文与产物须按项目保留策略独立归档。对要求持续幂等的请求，回执索引需覆盖协议承诺的重试期限。
- **共享实现。** Rust 内核维护权威转移规则，Node、Python、WASM、Rust SDK 对各自支持的入口传输引用与回执，复用同一组序列化、冲突和恢复样例。宿主 Memory 存储与父 Journal 分属两个提交域时，以幂等回执推进发布，持久化成功后才对外报告相应阶段完成。

## 7. 实施顺序与交付门槛

| 阶段 | 可独立交付的结果 | 进入下一阶段前的验收 |
| --- | --- | --- |
| P0 修复租约竞态 | 在 Node 内存实现中同步完成读取、校验、计数和回执登记。与文件版共用消费契约测试。 | 单额度、不同请求并发恰好一个获准；相同请求并发重投返回同一结果。接受事件数、额度消耗、回执一致。 |
| P1 版本化交接 | Rust 派发元数据携带产物身份与输入清单。Node 首先贯通依赖读取、full 继承、直接运行与 Harness 路径。 | 派发后父日志追加、同 key 内容替换、上游重试三种情况下，已启动 attempt 仍读取原定输入；旧日志恢复样例通过。 |
| P2 验证后完成 | 内核支持发行、替换和验证完成，接入父 Journal 的 prepare/commit、checkpoint 与 SDK 回执。此阶段形成首个可上线闭环。 | P1 报告无法完成 P2；两个竞争请求仅一次推进；无关对象可各自提交；持久化后崩溃、前缀裁剪后恢复、同请求重投均得到一致结果。对启用该能力的 SDK 运行同一组契约样例。 |
| P3 共享 Context / Memory 发布 | 为显式共享的结论 key 指定提交归属，候选通过审核后，按预期旧输出发布新版本。记录替代、反驳、验证的事实关系。 | 不同 key 独立更新；同 key 竞争者收到冲突并能重新提案；拒绝或过时的候选保留可追溯结果；现有读取权限、额度和删除策略继续生效。 |

试点优先选择已有 creator/verifier 工作流。观测指标包括旧产物完成请求的拒绝次数、同一请求重投命中数、因版本变化实际重跑的验证次数，以及派发清单对启动耗时和上下文 token 的影响。先用 P1 建立基线，再在同类工作负载上比较 P2。推广条件是能够从一次真实运行中回答：谁基于哪些输入产生了结果，哪份证据支持了最终完成，以及竞争提交为什么没有生效。
